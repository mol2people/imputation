## RF specifically

Tree building is CPU-bound and parallel over trees. 15–18 fat cores, huge L2, 307 GB/s — this is a good RF machine. No SMT, so `n_jobs` should be core count, not 2×.

- **15c:** roughly M4 Max laptop CPU class

`src/model.py` uses `RandomForestClassifier(random_state=…)` with default `n_jobs=None` → **1 core**. The hardware is idle unless you set `n_jobs=-1`.

## 24 GB is the real issue

Unified memory: OS + display compositor typically eat **4–8 GB**. Budget **~16–18 GB** for Python if Chrome is closed.

| Workload | 24 GB |
|---|---|
| One 100-tree RF, 16k × 400 | fine |
| 500-tree RF, unrestricted depth | fine |
| Grid + CV, `n_jobs=-1` on the forest | fine if outer loop is serial |
| Nested `Parallel(loky)` **and** `n_jobs=-1` on RF | can blow RAM (15–18 Python workers × copies) |
| Permutation importance with many repeats, parallel | RAM-tight before CPU-bound |
| Epoch-level matrices (10⁶ rows) or several forests in RAM | you will swap |

`feat_sel.py` already does the right thing: **`n_jobs=1` on the forest, parallelize over outer jobs**. Keep that pattern. Do **not** nest `n_jobs=-1` inside `joblib.Parallel`.

sklearn RF with `max_depth=None`, `min_samples_leaf=1` stores full trees. On 16k rows that is still small. If you ever fit on expanded epoch tables, switch to `HistGradientBoostingClassifier` (histogram, bounded memory) or cap `max_depth` / raise `min_samples_leaf`.

- **16"** (100 Wh, 140 W brick) sustains clocks better for hour-long grids.  
- Plugged in, lid open, low ambient: you get the Geekbench numbers. On battery, macOS will still run hard, but sustained all-core will drop.

## Practical take

For this project’s RF (participant-level, 10⁴ rows, 10² features): **excellent CPU, adequate RAM**. You will not wait on fits. You *will* wait if you oversubscribe workers or keep browsers + several 500-tree models resident.

## Compute

16 388 × ~167 after encoding is nothing. XGB `hist` on CPU finishes in seconds on this chip. The GPU never enters: XGBoost’s GPU path is CUDA. Switching learners does not use the M5 Pro any better than `RandomForestClassifier(..., n_jobs=-1)`.

## Signal, not learner

Test AUROC **0.713** (bootstrap SD 0.016) vs majority accuracy 0.669 and class-0 recall **0.25** is weak separation on coarse HR summaries plus source indicators. That is an information ceiling, not an RF ceiling.

Default sklearn RF (`max_depth=None`, `min_samples_leaf=1`, 100 trees) is an unregularized deep forest. On this \(n,p\) it almost certainly interpolates training labels. You did not report train AUROC; if it is ≫ 0.71, the live issue is **regularization**, which your sidequest grid (`min_samples_leaf`, `max_depth`, `max_features`) already targets. Untuned XGB (`max_depth=6`, `eta=0.3`) is just a different regularizer. A well-tuned RF and a well-tuned booster typically differ by **~0.01 AUROC** here, inside the bootstrap noise.

Val 0.668 vs test 0.713 (Δ = 0.045) is split luck or a source-mix fluctuation, not evidence that RF failed and boosting will fix it.

## Protocol

The frozen experiment is one default RF, no model comparison, test looked at once. Replacing it after seeing 0.713 is adaptive analysis. The sidequest is already a 48-config RF search on train+val with a frozen test. Adding XGB *and* selecting on the same holdout is a second peek.

If you want a booster, predeclare it as a **parallel family** on the same frozen split, same features, selection only on the tuning pool, one test look. Do not pick RF vs XGB from test AUROC.

## If you still want a booster

Prefer **`sklearn.ensemble.HistGradientBoostingClassifier`** over XGBoost for the first comparator:

- same environment, no extra dep
- histogram boosting ≈ LightGBM, which is the class that usually beats RF on tabular
- native NaN splits — **pass missingness through**; your median imputer + missingness indicators discard the one real advantage boosters have on this table
- early stopping on a inner val fold is the regularization that matters, not `n_estimators=500`

XGB is justified only if you want a second implementation family or monotonic/constraint knobs you will actually use. Then: `tree_method="hist"`, `n_thread` = core count, no `gpu_hist`, keep NaNs, modest `max_depth` (3–6), `eta` 0.03–0.1, early stopping. Defaults (`eta=0.3`, 100 rounds, depth 6) overfit about as readily as default RF.

## Higher-EV work than swapping the learner

1. Train AUROC / average tree depth of the current RF (diagnose overfit).  
2. Finish the RF grid; that is already the right regularizer search.  
3. Source-only vs physiology-only (you already flagged that source–salutation may dominate).  
4. For actual *imputation* of missing salutation: calibration and transport to the missingness pattern. AUROC on observed 10/20 does not identify that. Neither RF nor XGB solves MNAR.

**Bottom line:** keep RF as the primary. Do not run XGB to “use the Mac.” If you add a booster, add HGB with native missings as a predeclared comparator, not a replacement after looking at test.

**The MNAR information is mostly in the recording process, and the coverage gate throws the strongest piece of it away.** Switching learners or keeping per-column `__missing` bits is second-order.

Two processes, do not mix them:

| | What is missing | In this extract | Estimand |
|---|---|---|---|
| \(R_Y\) | salutation | **11 people** | transport / true imputation of unlabeled sex |
| \(R_X\) | wear, channels, adequate days | **everywhere** | discrimination of *recorded* salutation |

\(R_Y\) MNAR is not identified from labeled data without extra assumptions, and you barely have any unlabeled labels. What you can exploit is \(R_X \not\!\perp Y\).

## Empirical fact you already have

Among people with a binary salutation:

- eligible (≥14 adequate days): **33%** salutation 10  
- below gate: **54%** salutation 10  

\(P(\text{fail gate}\mid 10)\approx 0.30\), \(P(\text{fail gate}\mid 20)\approx 0.15\). Odds ratio \(\sim 2.4\).

That is a large, pre-model association between **thin recording and class 0**. Conditioning on the gate:

1. changes the target population,  
2. truncates \(R_X\) (remaining missingness indicators get low variance → A1 “drop `__missing`” looks harmless),  
3. collider-stratifies anything that jointly causes wear and salutation (device, occupation, overnight wear).

If the goal is to *use* MNAR, a 14-day hard gate is the opposite of that.

## What “benefit” means under MNAR

For **prediction of observed \(Y\)**, pattern-mixture is the right object:

\[
P(Y \mid X_{\mathrm{obs}}, R_X)
\]

You do not need to recover \(X_{\mathrm{mis}}\). Imputing \(X\) under MAR (MICE, median, RF-impute-then-classify) **averages away** the MNAR signal. Native-missing boosters help only insofar as they keep \(R\) in the split structure; they do not create information you deleted in aggregation.

For **imputing unlabeled salutation** (\(R_Y=1\)), MNAR means

\[
P(Y \mid X, R_Y=0) \;\neq\; P(Y \mid X, R_Y=1)
\]

No classifier fit on recorded 10/20 identifies that. Feature missingness does not fix it. You need a sensitivity model (δ-adjusted pattern mixture / selection model with an exclusion restriction), not XGBoost.

## Highest-EV use of \(R_X\)

**1. Put the gate back into the likelihood, or soften it (new predeclared analysis).**  
Fit on anyone with *some* valid HR, and let wear intensity be a predictor. The 5 299 excluded rows are the highest-information MNAR sample you have. A two-part model is cleaner than one RF on the truncated cohort:

- wear / coverage map \(R_X\) (possibly including “fails 14-day rule”),  
- physiology \(X \mid R_X\) only where measured.

Report both the gated estimand (current protocol) and the ungated one. Do not pick after seeing AUROC.

**2. Replace column-wise median + `__missing` with a *process* block.**  
Per-column NaNs after daily aggregation are a lossy coarsening of \(R_X\), and they are largely collinear with `adequate_days==0` / channel absence. Useful \(R\) is longitudinal and localized:

- calendar duty cycle, longest gap, start/stop (attrition vs never-wore)  
- **night-hour coverage** (watch-in-bed; typically the sex-differential MNAR)  
- weekend vs weekday coverage  
- which of {3000, 3001, 3002} exist — availability, not the imputed value  
- source as *mechanism*, not a dummy mixed across vendors  

Keep value features as NaN when the channel/day failed the rule. Do not median-fill. Then either HGB native missing **or** explicit “channel present” × value (no fill). Your A0 vs A1 test is only informative if the acquisition block is *removed* in one arm; otherwise you are dropping redundant bits.

**3. Predeclare an \(R\)-only baseline.**  
Same split, same protocol:

- \(R\)-only (acquisition + diurnal coverage + channel/source presence)  
- \(X_{\mathrm{obs}}\)-only (values, no \(R\))  
- both  

If \(R\)-only captures most of the 0.71 AUROC, the story is device/wear, not HR. That is the MNAR diagnostic. You already suspected source–salutation; this isolates it.

**4. Do not pool \(R\) across sources.**  
Apple point-event vs Garmin 1-min intervals are different missingness generators. A missing night on source 6 ≠ a missing night on source 3. Sole-source models (sidequest) are the right place to estimate \(P(Y \mid X_{\mathrm{obs}}, R)\). A pooled RF with source dummies assumes a common \(P(R \mid Y)\).

**5. Treat 3001/3002 availability as suspect leakage, not as extra physiology.**  
If vendor resting-HR uses entered sex, both the *value* and the *existence* of 3001/3002 can be MNAR-on-\(Y\) in the circular sense. Ablate: drop 3001/3002 **values** but keep their presence flags; then drop the flags too. If presence alone moves AUROC, you are reading the vendor stack, not MNAR wear.

## What not to do

- MICE / iterative imputation of HR summaries, then classify  
- Drop `__missing` because “hygiene” without an \(R\)-only control  
- Nested `n_jobs=-1` or XGB to “use MNAR”  
- Heckman/selection correction for this RF — needs an instrument for wear, different estimand  
- Claim transported imputation of missing salutation from a model fit on \(R_Y=0\)

## If you actually want unlabeled-sex imputation

With \(n_{R_Y=1}=11\), there is nothing to evaluate. If a later extract has real unlabeled mass, fit a **δ-adjusted pattern mixture**: parameterize \(P(Y \mid X, R_Y=1)\) as a tilt of \(P(Y \mid X, R_Y=0)\), vary δ over a predeclared grid, report the band. Identification will not come from \(R_X\).

**Bottom line:** MNAR helps only if \(R_X\) stays in the model and in the cohort. The 14-day gate spent most of that information on eligibility. Next analysis: ungated or soft-gated cohort, structured wear/diurnal-missingness block, \(R\)-only vs values-only, source-stratified, no MAR fill. That will move AUROC more than XGB vs RF, and it tells you whether you are imputing sex or imputing who wears a watch at night.
