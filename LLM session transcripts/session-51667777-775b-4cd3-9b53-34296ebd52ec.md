Happy to run it as an optional robustness variant (`feng_kfold`/`fsplit_kfold`), but I'd only bother if the 0.9% unscored users bother you — they're statistically indistinguishable from the rest by construction (random draws, no selection on features or outcome).

## User

do we at any point feed raw epoch timeseries to RF

---

## Assistant

No — never. The RF only ever sees the per-user tabular matrix; raw epoch series are consumed (and compressed) entirely upstream of any fit. Grounded in the code:

**Data flow** (`features.py` → `model.py` → `feat_sel.py`/`feat_eng.py`):
1. `EPOCH_DIR/out/<uid>.csv` — raw per-user epoch files — are read by `diurnal.py` (window parser) and `features.py`.
2. First compression: epochs → **epoch-day summaries** (daily mean/median/sd/hours per channel). Everything downstream is built from `days`, i.e., `features.py` groups by user×channel over epoch-*days*; epoch-level rows cease to exist at this step.
3. Second compression: day series → per-channel summaries (percentiles, sd of daily mean, weekday/weekend means, channel contrasts), tod shares (hour → 4 buckets: night/morning/afternoon/evening), and w7/w30 rolling window stats (mean/sd/min/max/slope).
4. `model.load_blocks()` loads the resulting `features_*.parquet` — one row per user — and that matrix (post `SQPreprocessor`) is the RF's entire world.

So the finest time resolution the forest ever sees is the **tod-bucket shares and weekday/weekend split of daily means**. No per-epoch rows, no sequences, no lagged/autocorrelation structure, no intra-day variability beyond 4 coarse bins. (`raw_manifest.py` touched raw files too, but only for the byte-size manifest and parser benchmark — no modeling.)

**Scoping implication for the conclusions we logged**: the §7–§10 "levers exhausted" verdict is a statement about the *daily-aggregate representation*. Anything epoch-scale — HRV, circadian amplitude/phase, intra-day variability, activity fragmentation, weekday-vs-weekend timing curves — was never in the feature space, so FS/FE null results don't bound what the raw signal could give. Extracting those would be a new upstream feature-construction phase (extension of `diurnal.py`/`features.py`), not another RF-side rearrangement — and it's the only remaining direction with genuinely new information content, at the cost of re-touching raw epochs for all 8,835 users.
